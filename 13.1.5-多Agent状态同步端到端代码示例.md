# 多 Agent 状态同步端到端代码示例

> 目标：用一个完整可运行的 Python 示例，把多 Agent 状态管理的真实逻辑串起来。本文配套代码是 [examples/multi_agent_state_demo.py](./examples/multi_agent_state_demo.py)，不依赖任何 Agent 框架，运行后可以看到完整状态变化和 event log。

---

## 一、为什么需要这篇

前面几篇文档讲了很多概念：

- State Catalog
- Context View
- State Patch
- Handoff Contract
- Artifact
- Event Log
- A2A Context Envelope
- Remote Result Import

但如果只看概念和框架片段，很容易仍然不清楚：

```text
Agent 到底读到了什么？
Agent 怎么提交更新？
系统怎么判断它能不能写？
A2A 返回 input-required 后本地状态怎么处理？
审批完成后怎么继续同一个任务？
远程 Agent 的结果怎么变成本地 state patch？
最终 event log 长什么样？
```

所以这篇给一个完整闭环。它不是伪代码，配套文件可以直接运行：

```bash
python3 examples/multi_agent_state_demo.py
```

## 二、示例业务：企业入职

场景：

```text
Alice 入职 Finance 部门
  -> HR Agent 收集入职表单
  -> IT Agent 需要开账号
  -> 因为是 Finance 权限，Security Agent 要求经理审批
  -> 经理审批
  -> Security Agent 完成审查
  -> 远程 IT Agent 通过 A2A 返回工单
  -> 本地系统导入远程结果
  -> Supervisor 汇总完成
```

这个例子故意覆盖几个关键点：

| 点 | 在示例里怎么体现 |
|----|------------------|
| 字段级权限 | `FieldRule` 控制谁能读写 `/employee`、`/approvals`、`/subtasks/it_account` |
| Context View | 每个 Agent 调用 `build_context_view(agent)` 只能看到授权状态 |
| State Patch | Agent 不能直接改 state，只能提交 `StatePatch` |
| 版本检查 | patch 带 `base_state_version`，旧版本会被拒绝 |
| Evidence | 写风险项必须引用 artifact |
| Reducer | 同一个 risk id 被再次写入时合并，而不是重复追加 |
| A2A input-required | 远程 IT Agent 在审批前返回 `input-required` |
| A2A result import | 远程 IT 结果通过 `a2a_importer` 转成本地 patch |
| Event Log | 每个 artifact 和 patch 都有事件 |

## 四、初始状态

示例初始状态：

```python
{
    "task": {
        "id": "onboarding_001",
        "goal": "Onboard Alice into the Finance department",
        "status": "submitted",
    },
    "employee": {
        "name": "Alice",
        "department": "Finance",
        "manager": "Bob",
        "start_date": "2026-07-01",
    },
    "subtasks": {
        "hr_profile": {"owner": "hr_agent", "status": "pending"},
        "security_review": {"owner": "security_agent", "status": "pending"},
        "it_account": {"owner": "it_agent", "status": "pending"},
    },
    "risks": {"register": []},
    "approvals": {"pending": [], "history": []},
    "artifacts": {"references": []},
    "final_message": None,
}
```

这里已经能看出几个状态边界：

- `task` 是全局任务状态。
- `employee` 是员工基础信息。
- `subtasks` 是多 Agent 分工状态。
- `risks.register` 是风险登记簿。
- `approvals` 是审批状态。
- `artifacts.references` 只放工件引用，不放大对象全文。
- `final_message` 只能由 supervisor 写。

## 五、State Catalog：谁能读，谁能写

`build_catalog()` 定义字段级权限。例如：

```python
FieldRule(
    prefix="/subtasks/security_review",
    readers=all_task_agents,
    writers={"security_agent"},
    consistency="strong",
)
```

意思是：

- 所有任务内 Agent 可以读安全审查状态。
- 只有 `security_agent` 能写。
- 这是强一致字段，不能用随便合并的方式处理。

再看风险字段：

```python
FieldRule(
    prefix="/risks/register",
    readers={"security_agent", "supervisor", "human_manager"},
    writers={"security_agent"},
    consistency="eventual",
    requires_evidence=True,
)
```

意思是：

- 风险不是所有 Agent 都能看。
- 只有安全 Agent 能写。
- 写风险必须带 `evidence_refs`。
- 这个字段可以用 reducer 合并，因为风险登记簿是列表型状态。

这就是状态治理的核心：Agent 不直接拥有 state，Agent 只拥有特定字段的读写能力。

## 六、Context View：Agent 不是拿全量 state

示例里每个 Agent 都通过：

```python
context = store.build_context_view("security_agent")
```

拿到自己的上下文视图。

Context View 包含：

```python
{
    "context_view_id": "ctx_security_agent_v2",
    "agent": "security_agent",
    "state_version": 2,
    "state": {...filtered_state...},
    "artifact_index": {...}
}
```

关键是 `state_version`。后续这个 Agent 提交 patch 时，必须声明自己基于哪个版本：

```python
StatePatch(
    patch_id="patch_security_requires_approval",
    actor="security_agent",
    base_state_version=context["state_version"],
    ...
)
```

如果别的 Agent 先改了 state，当前 patch 的 `base_state_version` 就会过期，系统会拒绝它：

```python
if patch.base_state_version != self.version:
    raise RejectedPatch(
        f"stale patch {patch.patch_id}: base={patch.base_state_version}, current={self.version}"
    )
```

这就是防止“旧上下文写入”的基础机制。

## 七、HR Agent：创建 artifact，然后提交 patch

HR Agent 做两件事：

1. 创建 `hr_form_v1` artifact。
2. 提交 patch，把 HR 子任务改成 completed，并把 artifact 引用写入 state。

核心逻辑：

```python
artifact = store.create_artifact(
    artifact_id="hr_form_v1",
    kind="form",
    producer="hr_agent",
    summary="HR onboarding form for Alice",
    data={"employee_name": "Alice", "department": "Finance", "manager": "Bob"},
)

patch = StatePatch(
    patch_id="patch_hr_profile_completed",
    actor="hr_agent",
    base_state_version=context["state_version"],
    evidence_refs=[],
    operations=[
        PatchOperation("replace", "/subtasks/hr_profile/status", "completed"),
        PatchOperation("replace", "/task/status", "working"),
        PatchOperation("add", "/artifacts/references/-", artifact.ref()),
    ],
)
store.apply_patch(patch)
```

这里的关键不是“HR 写了一句话”，而是：

```text
artifact.created
  -> state.patch.committed
  -> state_version 从 1 到 2
```

运行输出会看到：

```text
After HR patch
  /subtasks/hr_profile/status = completed
  /task/status = working
  /artifacts/references includes hr_form_v1
```

## 八、第一次 A2A 调用：远程 IT 返回 input-required

在安全审批之前，本地系统先尝试调远程 IT Agent。

先生成 A2A Context Envelope：

```python
first_envelope = build_a2a_context_envelope(store)
first_remote_result = remote_it_agent.handle_task(first_envelope)
import_a2a_result(store, first_remote_result)
```

envelope 里只放远程 IT 需要的最小上下文：

```python
{
    "goal": "Provision an IT account and laptop for Alice",
    "employee": {
        "name": "Alice",
        "department": "Finance",
        "manager": "Bob",
    },
    "approval_summary": [],
    "constraints": [
        "Do not access payroll data",
        "Provision Finance access only if manager approval exists",
    ],
}
```

注意没有传：

- HR 内部 prompt。
- Security Agent 的 scratchpad。
- 薪资信息。
- 全量聊天记录。
- 本地完整 state。

远程 IT Agent 的逻辑：

```python
finance_access_approved = any(
    item["type"] == "finance_role_access" and item["status"] == "approved"
    for item in approvals
)

if not finance_access_approved:
    return {
        "remote_task_id": "a2a_it_task_001",
        "status": "input-required",
        "input_request": {
            "reason": "Finance access requires manager approval",
            "required_approval_type": "finance_role_access",
        },
    }
```

本地导入逻辑不会强行改 IT 状态，只记录事件：

```python
if result["status"] != "completed":
    store.record_event(
        event_type="a2a.input_required",
        actor="a2a_importer",
        details=result,
    )
    return
```

这说明 A2A `input-required` 不是失败，而是一个同步点。

## 九、Security Agent：要求审批并写风险

Security Agent 看到 Alice 属于 Finance，但审批历史为空，于是：

1. 创建安全策略 artifact。
2. 把安全审查状态改成 `input_required`。
3. 写入风险登记簿。
4. 写入 pending approval。

核心 patch：

```python
patch = StatePatch(
    patch_id="patch_security_requires_approval",
    actor="security_agent",
    base_state_version=context["state_version"],
    evidence_refs=["artifact:security_policy_finance_access"],
    operations=[
        PatchOperation("replace", "/subtasks/security_review/status", "input_required"),
        PatchOperation(
            "add",
            "/risks/register/-",
            {
                "id": "risk_finance_access_approval",
                "severity": "medium",
                "status": "waiting_for_approval",
                "description": "Finance role requires manager approval before IT account provisioning",
                "evidence_refs": ["artifact:security_policy_finance_access"],
                "confidence": 0.98,
            },
        ),
        PatchOperation(
            "replace",
            "/approvals/pending",
            [
                {
                    "id": "approval_finance_access",
                    "type": "finance_role_access",
                    "requested_by": "security_agent",
                    "status": "pending",
                }
            ],
        ),
    ],
)
```

这里有两个关键检查：

### 9.1 权限检查

`security_agent` 能写：

- `/subtasks/security_review`
- `/risks/register`
- `/approvals/pending`

但不能写：

- `/subtasks/it_account`
- `/employee`
- `/final_message`

### 9.2 证据检查

风险规则要求 evidence：

```python
if rule.requires_evidence and not patch.evidence_refs:
    raise RejectedPatch(f"{operation.path} requires evidence_refs")
```

如果 Security Agent 不引用 `security_policy_finance_access`，patch 会被拒绝。

## 十、Human Manager：审批进入 history

人工审批不是一句“同意”，而是一个状态更新：

```python
PatchOperation("replace", "/approvals/pending", [])
PatchOperation(
    "add",
    "/approvals/history/-",
    {
        "id": "approval_finance_access",
        "type": "finance_role_access",
        "status": "approved",
        "approved_by": "Bob",
    },
)
```

这一步之后：

```text
pending approvals = []
approval history = approved
state_version 前进
```

Security Agent 再运行时，就能从 context view 中看到审批已通过。

## 十一、Security Agent 第二次运行：Reducer 合并风险

审批后 Security Agent 再次运行，这次它不会再要求 input，而是完成审查：

```python
PatchOperation("replace", "/subtasks/security_review/status", "completed")
PatchOperation(
    "add",
    "/risks/register/-",
    {
        "id": "risk_finance_access_approval",
        "severity": "low",
        "status": "mitigated",
        "description": "Manager approval exists, so Finance access can be provisioned",
        "evidence_refs": ["artifact:security_policy_finance_access"],
        "confidence": 0.99,
    },
)
```

风险项不是重复追加，而是通过 reducer 合并：

```python
def _append_or_merge_by_id(self, list_path: str, item: dict[str, Any]) -> None:
    items = get_value(self.state, list_path)
    for index, existing in enumerate(items):
        if existing.get("id") == item.get("id"):
            merged = {
                **existing,
                **item,
                "evidence_refs": sorted(
                    set(existing.get("evidence_refs", []) + item.get("evidence_refs", []))
                ),
                "confidence": max(existing.get("confidence", 0), item.get("confidence", 0)),
            }
            items[index] = merged
            return
    items.append(deepcopy(item))
```

所以最终风险项变成：

```python
{
    "id": "risk_finance_access_approval",
    "severity": "low",
    "status": "mitigated",
    "description": "Manager approval exists, so Finance access can be provisioned",
    "evidence_refs": ["artifact:security_policy_finance_access"],
    "confidence": 0.99,
}
```

这就是“同一事实/风险的状态演进”，不是两条互相矛盾的聊天记录。

## 十二、第二次 A2A 调用：远程 IT 完成

审批和安全审查完成后，再次构造 A2A envelope：

```python
second_envelope = build_a2a_context_envelope(store)
second_remote_result = remote_it_agent.handle_task(second_envelope)
import_a2a_result(store, second_remote_result)
```

这次 envelope 里有：

```python
"approval_summary": [
    {
        "type": "finance_role_access",
        "status": "approved",
        "approved_by": "Bob",
    }
]
```

远程 IT Agent 返回：

```python
{
    "remote_task_id": "a2a_it_task_001",
    "status": "completed",
    "data": {
        "account_status": "completed",
        "ticket_id": "IT-4242",
    },
    "artifact": {
        "artifact_id": "remote_it_ticket_4242",
        "kind": "ticket",
        "producer": "remote_it_agent",
        "summary": "IT account and laptop ticket for Alice",
        "data": {
            "ticket_id": "IT-4242",
            "account": "alice.finance.example",
            "laptop": "standard-finance-laptop",
        },
    },
}
```

本地导入不是直接信任远程结果，而是：

```text
remote result
  -> create local artifact copy
  -> build local state patch
  -> permission check by a2a_importer
  -> commit local state
```

导入 patch：

```python
PatchOperation("replace", "/subtasks/it_account/status", "completed")
PatchOperation(
    "add",
    "/artifacts/references/-",
    {
        "artifact_id": "local_copy_remote_it_ticket_4242",
        "kind": "ticket",
        "producer": "a2a_importer",
        "summary": "IT account and laptop ticket for Alice",
        "version": 1,
        "remote_task_id": "a2a_it_task_001",
    },
)
```

这一步展示了 A2A 和内部 state 的正确关系：

```text
A2A result 是外部输入
内部系统必须把它导入为受控 state patch
```

## 十三、Supervisor：汇总最终状态

Supervisor 读取所有子任务状态：

```python
statuses = {
    name: value["status"]
    for name, value in state["subtasks"].items()
}
```

如果全部完成：

```python
message = "Onboarding completed: HR profile, security review, and IT account are done."
task_status = "completed"
```

然后提交 patch：

```python
PatchOperation("replace", "/task/status", "completed")
PatchOperation("replace", "/final_message", message)
```

最终状态：

```python
"subtasks": {
    "hr_profile": {"status": "completed"},
    "security_review": {"status": "completed"},
    "it_account": {"status": "completed"},
}
```

## 十四、Event Log：系统为什么可审计

运行输出最后会打印 event log。关键事件顺序：

```text
evt_001 artifact.created by hr_agent
evt_002 state.patch.committed by hr_agent
evt_003 a2a.input_required by a2a_importer
evt_004 artifact.created by security_agent
evt_005 state.patch.committed by security_agent
evt_006 state.patch.committed by human_manager
evt_007 state.patch.committed by security_agent
evt_008 artifact.created by a2a_importer
evt_009 state.patch.committed by a2a_importer
evt_010 state.patch.committed by supervisor
```

这比“多 Agent 聊天记录”强很多，因为它能回答：

- 谁创建了哪个 artifact？
- 哪个 patch 修改了哪些路径？
- patch 基于哪个 state version？
- 哪些远程 A2A 结果没有导入，而是变成了 input-required？
- 最终 IT 状态是哪个远程 task 导入的？
- supervisor 的最终结论基于哪个版本？

## 十五、和主流框架的映射

这个示例是框架无关的真实逻辑。映射到框架时可以这样理解：

| 示例对象 | LangGraph | AutoGen | CrewAI | OpenAI Agents SDK | A2A |
|----------|-----------|---------|--------|-------------------|-----|
| `StateStore.state` | Typed State | 外部 task state | 外部 state store | 外部 task state | 调用方内部 state |
| `FieldRule` | 自定义 policy node | 外部权限层 | 外部权限层 | guardrail / tool permission | A2A server/gateway |
| `Context View` | node 输入 state projection | 发给某个 Agent 的消息上下文 | Task context | handoff input filter/context | Message DataPart |
| `StatePatch` | node 返回 state update | tool 写外部 state | task output 转 patch | tool/handoff result 转 patch | result import |
| `Artifact` | artifact store ref | file/message ref | task output artifact | file/tool output | A2A Artifact |
| `Event Log` | checkpoint + trace + app events | team state + app events | kickoff logs + app events | tracing + app events | task events |
| `RemoteITAgent` | A2A client node | 外部 agent call | external tool/task | hosted/remote handoff | remote A2A Agent |

关键结论：

> 框架可以帮你调度 Agent，但不会自动替你完成业务状态治理。状态目录、权限、patch、artifact、event log 仍然要由应用设计。

## 十六、自己动手改这个例子

建议你按下面顺序改代码，能更快理解状态管理：

1. 把 `SecurityAgent` 改成不带 `evidence_refs` 写风险，观察 patch 被拒绝。
2. 把 `HumanManager` 改成尝试写 `/subtasks/it_account/status`，观察权限被拒绝。
3. 在 HR patch 后保存旧 context，再让 Security 用旧版本提交 patch，观察 stale patch 被拒绝。
4. 把 `RemoteITAgent` 改成返回 `failed`，补充失败导入逻辑。
5. 增加 `FinanceAgent`，只允许它读写 `/payroll` 和 `/cost_center`。
6. 把 event log 输出改成 JSONL，模拟生产审计日志。

这些改动比直接看框架示例更有价值，因为它们会逼你面对真正的状态边界。
